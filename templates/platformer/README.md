# Platformer starter template

A small side-scroller to copy and grow. Run and jump across a Tiled level, collect coins, avoid
spikes and a pit, and reach the flag. It has one sound and one particle effect (both sent as
events), a one-line HUD, a result screen, an autoplay bot, a headless summary line and a rule test:
about 450 lines of C++ plus a 50-line test. `TODO` marks the places meant to grow.

| Path | What it holds |
|---|---|
| `CMakeLists.txt` | standalone project: the engine via `add_subdirectory` (or FetchContent), `lam_add_game` with a `SIM_LIBRARY`, the tests |
| `main.cpp` | presentation: `LevelScene`, camera, HUD, sparkle effect, sound bank, result screen, `--bot` / `--headless` wiring |
| `src/platformer/game.h` | every simulation type: `Player`/`Coin`/`Goal` tags, the `Level` resource, `Controls`, `Fx`, `LevelFinished`, `RulesPlugin`, `Bot` |
| `src/platformer/rules.cpp` | the rules (input to motor, coins, goal, spikes, pit), `start_level`, `summary_line` |
| `src/platformer/bot.cpp` | the autoplay `InputDriver` and its pure decision `bot_should_jump` |
| `tests/test_rules.cpp` | one doctest: a coin counts once and plays a sound, and the goal wins |
| `assets/prefabs.json` | `hero`, `coin`, `goal` (hand-written) |
| `assets/maps/`, `assets/sprites/`, `assets/sfx/` | generated by `tools/gen_assets.py` and committed |

## 1. Copy and rename

The name must be a C++ identifier (letters, digits, `_`) since it also becomes the namespace.

```sh
cp -R /path/to/LambdaEngine2D/templates/platformer ~/games/hopper
cd ~/games/hopper
mv src/platformer src/hopper
perl -pi -e 's/platformer/hopper/g' CMakeLists.txt main.cpp tests/CMakeLists.txt tests/*.cpp src/hopper/*
```

That renames the project, the targets (`hopper`, `hopper_sim`, `lam_hopper_tests`), the namespace,
include paths, system names, window title and summary prefix. Engine names like `PlatformerMotor`
are capitalised, so the rename leaves them alone.

## 2. Build

Inside the engine repository the default `LAMBDA_ENGINE_DIR` (`../..`) finds the engine:

```sh
cmake -S templates/platformer -B build/platformer -G Ninja      # Debug unless CMAKE_BUILD_TYPE is set
cmake --build build/platformer
```

- Copied elsewhere: add `-DLAMBDA_ENGINE_DIR=/path/to/LambdaEngine2D` (a checkout or a git
  submodule such as `external/LambdaEngine2D`).
- Offline: add `-DLAM_DEPS_DIR=<folder with the raylib, json and doctest archives>`, plus
  `-DFETCHCONTENT_BASE_DIR=<shared sources> -DFETCHCONTENT_FULLY_DISCONNECTED=ON` to reuse sources
  that were already fetched.
- No local engine: `CMakeLists.txt` has a commented FetchContent block. Pin `GIT_TAG` to a commit;
  replays are only valid within one build.
- Debug (the default) has the dev overlay (F3) and collider view (F4) and reads `assets/` from the
  source folder, so edits hot-reload. Release reads the copy next to the executable.

## 3. Run

```sh
build/platformer/platformer                                     # play
build/platformer/platformer --bot                               # watch the bot
build/platformer/platformer --headless --bot --frames 3000 --seed 7
#   platformer summary: ticks=<n> coins=<c>/<t> falls=<f> won=<0|1> hash=<16 hex>
```

Controls: A/D or the arrow keys to run, Space or Z to jump (hold for higher), S or Down to drop
through planks. Gamepad: left stick and South.

Headless runs have no window or audio, run one tick per frame, load assets synchronously and quit
when the level ends. Exit codes: `0` the level ended or `--frames` ran out, `1` startup failed
(e.g. prefabs didn't load), `2` no finish after 36000 ticks.

To check determinism, run the same command twice and compare `hash=`. `--hash-every 600` helps find
where two runs split; `--record-input run.lamr` and `--replay run.lamr` record and replay a run;
`--print-schedule` lists every system in run order.

## 4. Test

```sh
ctest --test-dir build/platformer --output-on-failure           # only this game's tests are registered
```

The test builds the world by hand and injects `TriggerEntered` events, so it needs no window, map
or assets. Add a `TEST_CASE` per rule.

## 5. How a tick flows

| When | System | Where |
|---|---|---|
| startup | push `LevelScene` (fresh World and asset scope) | `main.cpp` |
| `LevelScene::enter` | `start_level`: the `Level` resource and the `Tilemap`; camera and HUD entities | `rules.cpp`, `main.cpp` |
| FrameBegin (engine) | `tilemap_sync` fills `TileWorld` and spawns `hero`/`coin`/`goal` from the map's point objects | engine |
| TickBegin (engine) | `Bot::fill` with `--bot` | `bot.cpp` |
| Input | `player_input`: `InputFrame` to `PlatformerMotor` intent | `rules.cpp` |
| Simulate | `level_start`: respawn point, coin count, pit kill line (once) | `rules.cpp` |
| Physics (engine) | the motor moves the hero against tiles; `TriggerEntered`, `TileHazardTouched` | engine |
| PostPhysics | `touch_triggers` (coins, goal), `hazards` (spikes, pit) | `rules.cpp` |
| TickEnd | `on_level_finished`: push the result screen (headless: quit) | `main.cpp` |
| Update | `camera_attach` (-1350), `face_direction`, `hud_update` (-850) | `main.cpp` |
| Update (engine) | particles play `BurstAt`, audio plays `PlaySound` | engine |

Things the template already gets right:

- Rules emit `PlaySound` and `BurstAt` instead of calling audio or particles. `RulesPlugin`
  registers both events (idempotent), so the rules also run in tests without those plugins.
  Effect ids live in the optional `Fx` App resource.
- Every game system has `run_if = &has_local<Level>`. Plugin systems also run on the result
  screen's world, where `ctx.local<Level>()` would abort.
- `Level` uses `LAM_REFLECT` and `snapshot_resource`, so it is saved, undone and hashed.
  Presentation state (`View`) is a plain resource.
- Structural changes inside event loops and views go through `ctx.commands()` (`destroy`,
  `teleport`).
- Map rectangle objects spawn at their centre, so the generator writes point objects, at the feet
  for the hero. A motor body's `Transform` is its feet: `Collider` offset `{0, -half.y}` and the
  default `Sprite` pivot (0.5, 1).
- Pits need a kill line, because `TileWorld::outside_solid` makes the area below the map a floor.
- Paths inside an asset file are relative to that file (the `.tsj` `"image"`, the `.tmj` tileset
  `"source"`, the `.sounds.json` `"files"`). Paths in code and in `prefabs.json` are relative to
  `assets/`.
- Engine formats are strict. In a `.sounds.json`, `"groups"` is an object keyed by id; one bad
  entry fails all of `prefabs.json`.
- The bot clears only the device bits and keeps UI intents. It is declared before the `App` and
  reset after `run()`.
- The result screen is pushed from TickEnd, so replays reproduce it. The level world is a scene
  world, so the headless summary finds it in `world_stack()` after `run()` returns (worlds live
  until `~App`).

## 6. Assets

`python3 tools/gen_assets.py` (standard library only, deterministic) rewrites everything in
`assets/` except `prefabs.json`. Edit the `LEVEL` rows in the script: `#` ground, `=` one-way
plank, `^` spikes, `@` hero, `o` coin, `G` goal. To edit in Tiled instead, open `maps/level1.tmj`
and stop running the script, or it will overwrite your changes.

Tile collision comes from the tileset's tile properties: `shape` (`solid`, `one_way`,
`slope_up_right`, ...) and the bools `hazard`, `ladder`, `water` and `opaque`. An object's type
names the prefab to spawn. Commit the generated files; the build copies `assets/` and never runs
Python.

## 7. Grow it next

1. Lives and game over: add `lives` to `Level` and emit `LevelFinished{.won = false}` from
   `hazards` when they run out. The result screen already says "GAME OVER".
2. Checkpoints: a trigger prefab with a `Checkpoint` tag that sets `Level::respawn` in
   `touch_triggers`.
3. Enemies: a prefab with `PlatformerMotor`. A Simulate rule writes `move_x` and turns around on
   `on_wall_*`. Stomp with `CollisionStarted` in PostPhysics (RECIPES.md 2.5).
4. Animation: an Aseprite sheet plus an `.anim.json` graph, and `Animator`, `AnimParams` and
   `MotorAnimBridge` in the hero prefab. Then delete `face_direction`, since the animators own
   `kFlipX` (set `Animator::facing`). `.anim.json` is strict and its `"sheet"` path is relative to
   the `.anim.json` file.
5. Moving platforms: `MovingPlatform`, `PathFollower` and a one-way `Collider`. Add `Velocity` too,
   or the platform is a Static body.
6. More levels: give `LevelScene` a level index and `replace` it with the next one on a win.
7. Pause menu: push a `MenuScene` overlay from an Input system (RECIPES.md 2.9).
8. Camera shake: rules emit a game event and Update adds to `CameraShake::trauma` (RECIPES.md 2.3).

`examples/games/06_platformer` ("Hop Hill") already does 1 to 5, and the engine's `docs/RECIPES.md`
has a recipe for each.
